# The teaching evaluation loop - traceability as a product feature

Written 2026-09-27, **before any run in this document was launched**. Sections
1-4 are the problem statement and the pre-registered protocol; section 5 is
filled in afterwards from the evidence under
[`evidence/teaching-loop/`](evidence/teaching-loop/) and says so.

## 1. The problem statement

> **An author who changes an agent cannot tell whether the change made the
> workflow better, and cannot show anyone else why.**

Crew Studio already records everything needed to answer that question, in three
places that were built separately:

| Source | What it knows | What it cannot know alone |
| --- | --- | --- |
| **The app** (PostgreSQL `runs`, frames, `document_version`) | which version of which workflow ran, on what input, what it answered, who rated it | what the provider actually billed |
| **Langfuse** (one session per run, `sessionId = run_id`) | the trace tree - run → node → task → agent → generation - timings, and the `human_rating` score | which workflow version is better; it has no notion of a change |
| **OpenRouter** (`GET /api/v1/generation`) | the billed cost and the serving provider of every call | anything about the workflow at all |

Separately each is a dashboard. **Joined on `run_id`, they are an
experiment**: a version is the treatment, the rating is the outcome, the trace
is the explanation, and the billed cost is the price. The enhancement this
document proves is not new plumbing - it is using the plumbing as a loop:

```text
 author a workflow ─► run it on a fixed set of inputs ─► rate each run by a rule written first
        ▲                                                           │
        │                                                           ▼
 change ONE thing ◄── read the traces of the Bad runs ◄── Compare v1 vs v2 (app)
                                                        + billed cost (OpenRouter)
                                                        + human_rating on each trace (Langfuse)
```

Every workflow in the product benefits, because nothing in the loop names a
workflow: identity is copied off the CrewAI event (C1 of
`DEFINITION-OF-DONE.md`), versions are stamped at launch, and Compare, Export
and the model review take a `workflow_id`.

## 2. The worked example: a formative-feedback tutor

Teaching is the right first domain because it has a well-known failure mode that
**looks like success to a casual reader**: a "helpful" tutor that tells the
student the answer. The feedback reads fluent and correct, and it removes the
productive struggle the feedback exists to create. A reviewer skimming outputs
rates it good; a teacher with a rule rates it bad.

The workflow is `data/examples/teaching/formative-feedback-tutor.v1.json`
(v2 beside it), generated by `scripts/observability/teaching_loop.py emit`:

```text
submission (input: question + the student's answer)
  → Teacher check (gate: a human approves before anything is billed)
  → Assess     (agent, cheap tier, output_schema {verdict, misconception, next_step})
  → Verdict    (transform: pick verdict)
  → Tutor      (agent, cheap tier, writes the feedback for the student)
  → Report     (transform: format "DIAGNOSIS … FEEDBACK FOR THE STUDENT …")
  → Feedback   (output)
```

Every node is a real CrewAI primitive (plan 00 D3): two `Agent`/`Task` pairs, a
`@human_feedback` gate, and compiler-owned transforms.

**v1 → v2 is ONE change**: the Tutor node's backstory, task description and
expected output. v1 is the tutor most people write first ("explain what they got
wrong, show the working, state the correct answer"). v2 is formative feedback:
name the misconception, give one hint, ask one guiding question, do not state
the final answer, at most 90 words. The Assess node, the models and the graph
are identical.

## 3. The pre-registered rule

Eight submissions, fixed in `data/examples/teaching/submissions.json`, each with
the teacher's expected verdict and, for wrong answers, a pattern that matches
the correct final answer. A run is:

- **Bad** if the assessor's verdict disagrees with the teacher's
  (`correct` vs not-`correct`), **or**
- for a wrong answer: **Bad** if the student feedback contains the answer
  pattern (the answer was given away), **or** contains no question mark (it asks
  the student nothing), **or** is longer than 120 words;
- for a right answer: **Bad** if the feedback is longer than 120 words;
- **Good** otherwise. **Not sure** is used only when the run did not finish.

The rule is code (`judge()` in the driver) so it is applied identically to both
versions and to every run, and its reasons are written into the rating note.

**Prediction, written now:** v1 leaks the answer on most of the six wrong
submissions and is often over 120 words; v2 fixes the leak. The assessor should
be right on nearly all eight in both versions, because it did not change.

## 4. Money and environment

- Local **paid** backend on port **8011** (not :8000, not the E2E port), real
  engine, `SYNTHETIC` unset, authenticated by the local JWKS stand-in
  (`scripts/observability/mint_identity.py`) so the caller has an identity and
  can be the admin for Compare / Export / model review.
- Models: the cheap tier (`CHEAP_MODEL`) on both agents; the model review is one
  cheap-tier `LLM.call` capped at $0.05.
- **Estimate before running:** 16 runs × ~3 cheap calls × ~1.5k tokens ≈ 72k
  tokens ≈ **$0.02**, plus one review ≈ $0.002. Ceiling for this session:
  **$0.25**, checked with OpenRouter key usage before and after.
- Langfuse: the local `.env` keys, `environment = live`, so each run is one
  session on `us.cloud.langfuse.com`.

### 4a. v3, pre-registered after reading v2's one Bad run and before running v3

v2 was 7/8 Good. The one Bad run (`s3-seasons`) is a real leak, not a rule
false positive: the guiding question was *"How does the tilt of Earth's axis
change the intensity of the sunlight…?"* - the answer, inside the question. In a
procedural item a method hint does not reveal the result; in a conceptual "why"
item the key term IS the answer, and v2's "name the misconception" pushed the
model to name the concept.

**v2 → v3 is ONE change, again to the Tutor task only**: one sentence added -
*for a "why" or "what" question, do not name the scientific term or quantity
that answers it, even inside the hint or the question; point the student at
something they can observe or check instead.* All eight submissions are re-run,
because a fix for one item must be shown not to break the other seven.
**Prediction:** 8/8, with feedback length unchanged.

### 5a. What each source contributed, and what it could not

- **The rule-based rating (the app's `human_rating`, written by `judge()`)**
  was the only signal that found the defect. Everything operational was
  perfect in v1: 8/8 completed, 0 failures, 0 tool failures, 0 guardrail
  retries, gate revise rate 0.0.
- **Compare** turned "I edited a prompt" into a measured before/after per
  version: Good 1 → 7 → 8, cost per run roughly halved, and neither arm flagged
  as underpowered at n = 8.
- **Langfuse** holds one `live` session per run (`sessionId` = run id,
  `userId` = the caller), the run → node → task → AGENT → GENERATION tree, and
  the `human_rating` score on each trace (`bad` on v1 s1, `good` on v3 s1),
  beside `gate_outcome: approve`. So a Bad trace in Langfuse is one click from
  its reason.
- **OpenRouter** priced every generation. `cost_source` is `openrouter-billed`
  on all four generations pulled, served by Google AI Studio. The unchanged
  **Assessor is a built-in control**: about $0.0003 a call in v1 and v3, while
  the edited Tutor fell from $0.0011 to $0.00032. The saving is the change, not
  noise.
- **The model review** is blind by design (plan 21 R2: counts only, never
  content). It reported "24 of 24 completed with zero failures" and could only
  say "investigate the 8 Bad runs". Its sentence "rests on fewer than five runs"
  about eight Bad runs is wrong. It says what to look at; it cannot say why.

### 5b. Defects in the platform that the loop found, and fixed here

1. **Every gate timestamp was off by the host's UTC offset.** CrewAI stamps
   `PendingFeedbackContext.requested_at` with a naive `datetime.now()` (local
   time), and the registry labelled it UTC. On this UTC+8 machine every gate's
   `opened_at` and `expires_at` was stored 8 h in the future, and hotspots
   reported the Teacher check's median wait as **−28,798.5 s**. West of UTC the
   same arithmetic puts `expires_at` in the past, so a gate would expire as soon
   as it opened. Render's clock is UTC, which is why production never showed it.
   Fixed with `registry._crewai_clock_utc` at the three call sites. The gate id
   still hashes the raw stamp, so a replayed gate keeps its id.
   `tests/service/test_gate_clock.py` pins the zone (UTC+8 and UTC−5), so it
   bites on a UTC CI runner too. Reverting only the `expires_at` call site fails
   2 of its 7 tests. `expires_at` is now served with `+00:00`. The two
   `test_builder_gates` expiry tests that subtracted the naive stamp now compare
   in UTC.
2. **Gate hotspots never aggregated.** Rows were bucketed on `gate_id`, which
   the registry mints per run, so 24 runs showed as 24 rows of `opened: 1`. The
   test passed because its seed gave all six runs the same literal id, which
   production never does. Rows are now bucketed on the canvas node.
   `GateBucketedByNodeTests` uses per-run ids and fails on revert.

**Verified live after the fix**, on a restarted backend running the fixed code,
with one more real run (`post-fix-run.json`, s3 again, Good). It was launched at
07:34:56.6Z. Its gate is stored `opened_at` 07:34:58.1Z (it had been stored as
15:23), `expires_at` exactly 1800 s later, and answered 0.30 s after opening.
`hotspots-after-fix.json` shows **one** `teacher_check` row with 25 openings
(`hotspots-before-fix.json` had 24 rows of 1). Its median is still −28,798.5 s,
because the 24 older rows were written with the wrong clock and the fix does not
rewrite history. A backfill is `opened_at - offset` for rows written by a non-UTC
host, and only the operator knows which host that was, so none was attempted.

448 tests over every gate, improve, evalset, admin-decision, retention, restart
and revise module pass (`DATABASE_URL=sqlite+pysqlite:///:memory:`), and
`emit_improve_fixture.py --check` is current.

### 5c. Found, not fixed (the next change)

- **Langfuse cannot tell versions apart.** The trace's tags are
  `gates:human, mode:run, ug_2805daab`, and no metadata carries
  `document_version`. Langfuse can filter to `human_rating = bad`, but not to
  "v1 only". Today the version join exists only in the app's Compare. The fix is
  a `version:<n>` tag on the trace, and it is a TRACE-CONTRACT amendment, so it
  is recorded here rather than built.
- **A regex rule is a floor, not a judge.** It caught the conceptual leak
  because the teacher wrote the term into `answer_pattern`. A paraphrase ("the
  way Earth leans") would pass. The Good runs exported in `evalset-good.ndjson`
  (16 lines plus the header) are the starting set for a stronger grader.
- **The dev database's gate backlog** (405 expired gates at boot) is remaining
  work item 66's residue, not this loop's.

PR #37 merged as `76a3e88`. The API (`agentic-crew-ai-api`, starter) went from
build to live in about 2 minutes (09:13:30Z → 09:15:34Z, Render API). The studio
(free tier) was correctly **not** redeployed: it has `rootDir: frontend` and the
merge touched nothing under `frontend/`. Its first request after sleeping took

id is replaced with `<owner-user-id>` throughout `evidence/teaching-loop/production/`.

**Finding: production pays about 1.8× what the app estimates.** Langfuse's
billed totals are $0.001375 and $0.001162. The app's estimates are $0.000764 and
$0.000646. Production was served by provider **"Google"**; the local runs were
served by **"Google AI Studio"** and billed at the estimate. `:nitro` routes on
speed, not price. This is the 1.8× priority-endpoint finding of the
observability programme, met again. So Compare's `cost_per_run` (an estimate)
understates production spend by about 45%. The billed figure in Langfuse is the
true one. Recorded, not changed: pricing policy is the owner's call (audit M14
already prices the static estimate at the dearest endpoint).

## 6. How to reproduce

```bash
# 1. identity stand-in (keep running)
./.venv/Scripts/python.exe scripts/observability/mint_identity.py serve --port 8093
# 2. paid backend (a second shell)
export AUTH_BASE_URL=http://127.0.0.1:8093 PORT=8011 ADMIN_EMAILS=teaching-proof \
       IMPROVE_DIGEST_ENABLED=1 CREDENTIALS_MASTER_KEY=<base64 of 32 bytes>
./.venv/Scripts/serve.exe
# 3. the loop (~$0.01 per version of 8 runs)
./.venv/Scripts/python.exe scripts/observability/teaching_loop.py emit
./.venv/Scripts/python.exe scripts/observability/teaching_loop.py run --versions 1 2
./.venv/Scripts/python.exe scripts/observability/teaching_loop.py run --versions 3 --resume
./.venv/Scripts/python.exe scripts/observability/teaching_loop.py evaluate --a 1 --b 3 --review
```
