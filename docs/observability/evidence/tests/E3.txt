4. The new thing: the credential-prefix BOUNDARY, and why the two copies differ
--------------------------------------------------------------------------------

58a1c0b gives both the redactor and the scanner a token boundary, to stop a hex
UUID being mangled - a real defect, and a bad one: run id
1a0bea14-ffb3-459d-b5fc-f714a76e5f71 contains 'fc-' at offset 21 and was written
to disk as ...-b5<redacted> in eleven committed files, one of them the
langfuse-session.json 'id' that row A1 is verified on.

But the two copies apply it DIFFERENTLY, and the divergence is deliberate and
documented at content.py:63-84:

  src/brief_crew/observability/content.py   boundary on 'fc-' ONLY
  scripts/observability/_common.py          boundary on EVERY prefix

V-REVIEW ran both patterns over eight strings rather than reading them:

  string                                   | content.py (redactor) | _common.py (scanner)
  -----------------------------------------+-----------------------+----------------------
  a planted key INSIDE an id (my probe)    | BLANKED               | NOT blanked   <-- differs
  a key in JSON                            | BLANKED               | BLANKED
  a UUID that contains fc-                 | NOT blanked           | NOT blanked
  a firecrawl key, quoted                  | BLANKED               | BLANKED
  a firecrawl key glued after hex          | NOT blanked           | NOT blanked
  an fc- key with a NON-hex tail           | NOT blanked           | NOT blanked
  a github token inside an id              | BLANKED               | NOT blanked   <-- differs
  a bare prefix written in prose           | NOT blanked           | NOT blanked

V-REVIEW AGREES WITH THE NARROWING, and would have raised it as a finding had it
not been made. Three reasons, in the order they matter:

1. **A blanket boundary is a false NEGATIVE in a redactor, and a redactor's
   false negative is a disclosure.** Rows 1 and 7 above are the measurement: a
   credential glued after a hyphen inside an identifier - `gate-sk-or-v1-...`,
   `user-ghp_...` - survives the scanner's pattern and is caught by the
   exporter's. That is not a hypothetical: `e3_planted_key_probe.py` has planted
   exactly `gate-<key>` since its first run, an hour before this rule existed,
   because a gate id is author-controlled and an author can paste anything into
   one. Under a blanket boundary that probe would have reported six leaking
   conditions again.
2. **The narrowing costs nothing it was buying.** The boundary exists to protect
   a hex UUID, and a UUID contains nothing but hex and hyphens, so `fc-` is the
   only one of these prefixes that can occur inside one. Row 3 shows the UUID is
   still safe with the boundary applied to `fc-` alone. Applying it to `sk-or-`
   or `ghp_` protects nothing that exists.
3. **The asymmetry is stated where a reader meets it**, in both files, with the
   argument and the measurement rather than a cross-reference. Two spellings of
   one rule that agree by accident is the failure mode this repository has paid
   for; two that differ ON PURPOSE and say so is the opposite.

WHAT THE SCANNER'S BLANKET BOUNDARY DOES COST, and it is worth a note in
INDEX.md because `_common.py` wears two hats in one module:

* As a SCANNER (secret_scan.py's WARN channel), a false negative costs a warning
  nobody needed. Harmless, and it is what the boundary was for.
* As a REDACTOR - `CREDENTIAL_REDACTION_PATTERN`, reached through
  `redact_string` and `redact_for_disk`, which is what `pull_langfuse_run.py`
  uses to write pulled Langfuse exports INTO `docs/observability/evidence/` - a
  false negative writes a credential into a committed file. Rows 1 and 7 are
  that class.

Bounded, and this is why it is LOW rather than MEDIUM: `redact_string` runs the
exact-VALUE rule FIRST and unconditionally, so any credential this process holds
is blanked wherever it sits, boundary or no boundary. The residual is a
credential the process does NOT hold - a key a user pasted, echoed back by the
Langfuse API - sitting glued after an alphanumeric or a hyphen. And the app-side
exporter now scrubs exactly that on the way OUT, so it should never have reached
Langfuse to be pulled back. The tooling redactor is the second line here, not
the first. Worth one line in INDEX.md so the next person to touch _common.py
knows which of its two hats the boundary was chosen for.

ONE FALSE NEGATIVE BOTH COPIES SHARE, and neither documents: row 6. `fc-` now
requires 20+ HEX characters, so a Firecrawl key whose tail is not hex - or a
future key format that is base62 - is invisible to both. A real fc- key is
32 hex today, so this is a bet on the vendor's format rather than a defect, but
it is a bet, and the exact-value rule is what covers it in the meantime.
