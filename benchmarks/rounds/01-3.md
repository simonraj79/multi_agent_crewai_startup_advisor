## Verdict, clause by clause

**A — `endSession` ends the token and nothing else: ABSENT.** `useAuthGate.ts:98-119` now
reads the identity, calls `clearAccessToken()`, then `forgetIdentity(identity)` *before*
`signOut()`. Measured, not read: one click on the account chip's sign-out removed **eight**
keys across both storages — Alice's four scoped keys and all four planted legacy shapes —
and kept exactly the two that are nobody's (`builder-vocabulary`, one build of the server's
reply) plus Bob's own scoped session id. The order matters and holds: the id is read before
`signOut` revokes the session, so the sweep still knows whose prefix to walk.

**B — the next person inherits the draft with the credential id: ABSENT.** The draft is
still written for a *saved* document and still holds `config.credential_id` in plaintext
(1362 bytes, `contains cr_d1795e63? true`) — that part of the row's description is
unchanged and was never itself the defect. What changed is the key: `u:vdalice:builder-draft:ug_82701ab2`.
After the swap, Bob's readable set is exactly `["builder-vocabulary","u:vdbob:validator-session-id"]`,
his own `builder-draft:` key reads `null`, the builder offers no restore bar and his library
is empty. Alice's copy is still on disk under her prefix, which is the control proving this
was one browser profile and not a fresh one.

**C — the run pointer and the handoff banner cross the identity change: ABSENT.** Bob's
console after the in-place swap: no run id rendered, no handoff banner, no error banner, no
gate card, badge `idle`, button `Launch`. The row's three measured strings are all gone.
The control rules out a false negative: the *same* handoff record written under Bob's own
key renders `Running your published graph vdalice gated graph. It asks for idea.` — so the
banner works and its absence in the previous step is scoping, not breakage.

**D — a refused restore still prints the previous run id under "Relaunch": ABSENT.** With
Bob's own correctly-scoped pointer aimed at a run the server 404s, the console shows the
server's sentence `run not found`, badge `error`, button `Launch` (not `Relaunch`), the
status panel's markup does not contain the refused id anywhere, and the pointer is cleared
from storage. Both halves of the fix are visible in source: `runId.value = ''` in the
`catch`, and `primaryLabel` now requires `runId.value` as well as a terminal status.

**Beyond the row, the upgrade path also holds.** The scoping fix keys new writes, so a
browser carrying an *older* build's bare keys is the case where "the next person inherits"
could still have been true with nothing swept. It is not: Bob signing in over Alice's
legacy `validator-active-run`, `validator-session-id`, `builder-draft:<id>` and
`builder-run-handoff`, with no sign-out in between, gets an idle console, an empty builder,
and — even deep-linking her document id — a canvas with zero nodes and no mention of her
credential id in the DOM.

**No trade found on the same surface.** The three candidates I checked and rejected:
Bob's own scoped session id survives Alice's sign-out (correct — it is his); the
sign-out sweep does not touch `builder-vocabulary` or the minimap preference, neither of
which belongs to a person; and there is no anonymous-then-sign-in draft-loss path in
practice, because `App.vue` gates both views behind `authPhase` and never renders them
while the session is `checking`, so a signed-in write can never land under the bare key.

## What I could not verify, and why

- **A real Google sign-out.** No OAuth client runs in this harness; the identity is the
  synthetic-user cookie, and the "sign-out" I exercised is `endSession` reached through the
  product's own account-chip button. That is the same function a real sign-out calls, and
  the sweep happens before `signOut()` — so the browser-side result cannot differ — but the
  server leg of a real Google sign-out was not exercised. The row itself was measured the
  same way and says so.
- **Two separate OS users / two profiles.** Out of scope by construction: the row is about
  one shared browser profile.
- **At-rest exposure, which is not the row's defect but is worth naming.** Alice's draft
  still sits in `localStorage` in plaintext, credential id included, until *she* signs out
  on that machine. Another person with devtools on the shared profile can still read it;
  what they can no longer do is have the application hand it to them. The row's own located
  evidence is entirely application-level reads ("the console printed", "the banner said",
  "storage still held … contains cr_…? true" as read back by the page), and the row's own
  closing sentence calls it "client residue", so I judge the clause on inheritance rather
  than on encryption at rest. If the intent was "no credential id in plaintext on a shared
  profile at all", that is a different and still-open requirement, and it is not what this
  row's sentence says.
- **Legacy bare keys are inert but persistent.** They are not readable by any signed-in
  user, and they are swept by the next sign-out by anybody — which also means one person's
  sign-out deletes another person's legacy draft. That is data loss on an upgrade path, not
  a leak, and the commit states losing unsaved work on sign-out is the intent.
